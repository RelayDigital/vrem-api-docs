# MCP Server

Vremly ships a [Model Context Protocol](https://modelcontextprotocol.io) server,
so an AI assistant can work with your projects, customers, media and invoices
directly instead of you copying data between it and the app.

It is a client of this same REST API. Everything on this page is governed by
the API key you give it — the assistant has exactly the access that key has,
and no more.

## What approving actually grants

Approving a connector creates an ordinary **API key** in your organization,
named after the assistant. That is the entire grant — there is no separate
&ldquo;connector permission&rdquo; with rules of its own.

Which means everything you already know about keys applies unchanged:

- it belongs to **one organization**, and the server derives that organization
  from the key, so an assistant cannot reach another one
- its **scopes are enforced on our servers**, on every request
- it appears in **Settings → Developers → API Keys** beside your other keys
- **revoking it there disconnects the assistant immediately**

Read-only is preselected on the approval screen. Write access is a deliberate
choice, and worth declining unless you need it — see
[Permissions](#permissions) for why that matters more with an assistant than
with your own code.

## Local install configuration

Environment variables for the **local install** only. The hosted connector
needs none of these — it is configured by the approval screen.


| Variable | Default | Purpose |
|---|---|---|
| `VREMLY_API_KEY` | *(required)* | Your organization API key. |
| `VREMLY_API_URL` | `https://api.vremly.com` | API base URL. |
| `VREMLY_MCP_READ_ONLY` | unset | `1` refuses anything but `GET`/`HEAD`/`OPTIONS` and a short list of reviewed preview `POST`s that change nothing, such as `/orders/prepare`. |
| `VREMLY_MCP_TIMEOUT_MS` | `30000` | Per-request timeout. |
| `VREMLY_OPENAPI_PATH` | bundled | Point at a different OpenAPI document. |

## What it exposes

Four tools, not one per endpoint:

| Tool | Purpose |
|---|---|
| `vremly_capabilities` | The connected organization and the permissions this connection holds. |
| `vremly_search_endpoints` | Find endpoints by keyword. |
| `vremly_describe_endpoint` | The endpoint's parameters, required body fields and responses. |
| `vremly_request` | Call it, and return the status and body. |

The API has hundreds of operations. A tool per operation would cost more
context to list than most tasks cost to do, and many assistants cap how many
tools they will accept. Capabilities → search → describe → request reaches all
of them at a fixed cost, and because the search reads the OpenAPI document
directly there is no generated tool list to fall out of date.

:::tip Describing before calling is not optional
A guessed body field fails one of two ways. Where the endpoint publishes a body
schema, an unknown field is rejected with `400` and nothing changes. Where it
does not, the field is **ignored** and the call can still return `2xx` having
skipped it. `vremly_describe_endpoint` says which applies to each operation,
and is what stops an assistant guessing.
:::

## Prompts

The hosted connector also offers ready-made prompts. Each one names the
endpoints and fields to use, so the assistant does not have to discover them.
Hosts that support MCP prompts show them as commands you can pick.

| Prompt | What it does |
|---|---|
| `just-listed-post` | Gets your latest listing's Just listed post: the story and feed images, the caption, and the facts to design your own. See [Share Cards](/guides/share-cards). |
| `delivery-summary` | What was delivered over a period, and to whom |
| `upcoming-schedule` | What is booked, when, and who is on it |
| `project-status` | Everything current about one job |
| `outstanding-invoices` | Who owes money, how much, and how overdue |
| `cash-position` | What is owed, how overdue, and how fast it collects |
| `profitability` | Gross profit per job, and which clients fund the business |
| `turnaround` | Delivery speed, and how often the promise is missed |
| `bottleneck` | Where jobs are queuing: booking, shooting or editing |
| `crew-load` | Who is overloaded in the next 7 days |
| `client-concentration` | How exposed the business is to its biggest customers |
| `client-health` | Who is active, slipping, or gone |
| `prepare-booking` | Prepares a complete booking and quote without creating anything |
| `prepare-shoots` | Checks upcoming shoots for staffing, calendar and equipment problems |
| `manager-review-brief` | Overdue reviews, unanswered questions and blockers |
| `build-evaluation-rubric` | Drafts an evaluation rubric for you to approve |

You do not need a prompt to ask for a share card. Things people say, and what happens:

| You say | What the assistant does |
|---|---|
| "Get my just-listed card for 123 Main St" | `GET /me/share-cards?kind=JUST_LISTED`, then `GET /me/share-cards/just-listed/{projectId}`; returns the image URLs and the caption |
| "Make me a carousel caption and three slide designs for my new listing" | Reads the same card and builds the slides from `data.gallery`, `data.facts`, `data.agent` and `caption`, in its own tool |
| "Write an email blast announcing it" | Uses the card's facts and `links.listingUrl` exactly as given, so visits from the email are tracked |

The share-card requests read your own listings across every media company you
order from, so they need the connector approved on your **personal workspace**.
Approved on a company workspace, the assistant reads a listing's card through
`GET /listings/projects/{projectId}/share-cards/just-listed` instead.

## Permissions

**What the assistant can do is decided by the key, checked on our servers, on
every request.**

| Scope | Grants |
|---|---|
| `READ` | `GET`, `HEAD`, `OPTIONS` |
| `WRITE` | Everything `READ` allows, plus `POST`, `PUT`, `PATCH`, `DELETE` |
| `ADMIN` | Everything, except moving money (below) |
| `BULK_IMPORT` | The bulk import endpoints only |
| `WEBHOOKS` | Managing webhook subscriptions |

Keys can also hold narrower grants for one business area, such as
`EVALUATIONS_WRITE`, which allow that area's reviewed operations and nothing
else. `vremly_capabilities` lists what a connection holds.

A key belongs to one organization and the server derives the organization from
it, so the assistant can never reach another organization's data.

**An assistant cannot move money, at any scope.** It cannot charge a card,
issue a refund or take a card-reader payment; the server refuses those to every
key. To get paid it sends the customer a payment link. If it cancels a job that
is already paid, the job is cancelled, the invoice stays paid, and your
business gets an email to issue the refund in Vremly. It never charges a
cancellation fee either. See
[Authentication](/guides/authentication#what-no-key-can-do-move-money).

:::warning Give it a READ key unless it needs to write
That is the guarantee that holds even if the assistant is prompt-injected by
something it reads — a listing description, an email, a web page. A read-only
key cannot be talked into deleting a project, because the refusal happens on
our servers and not in the assistant's judgement.

`VREMLY_MCP_READ_ONLY=1` is a convenience, **not** a security boundary:
anything able to set that variable could also unset it. The key's scopes are
the boundary.
:::

:::danger An `ADMIN` key can mint more keys
Revoking a leaked `ADMIN` key does not necessarily contain it, because it may
already have issued others. Grant it only when something genuinely needs
organization-level settings.
:::

Requests are rate limited per key: each key has its own per-minute budget,
120 by default, and some endpoints add their own cap. See
[Rate Limits](/guides/rate-limits).

## Verifying a local install

The hosted connector needs no verification step — if Claude shows it as
connected, it is. For a local install, the server writes a status block to
**stderr** on start — never stdout, which
carries the MCP protocol itself. Run it directly to see it:

```bash
VREMLY_API_KEY=your-api-key npx -y github:RelayDigital/vremly-mcp
```

It appears to hang after printing. That is correct — a stdio server waits on

The key line is the one worth reading. The server reports ready whether or not
a key was supplied, because dying during the handshake surfaces in most hosts
as an unexplained "server failed to start" with the real reason lost. If that
line shows a warning, the server is fine and the environment is not — the host
is not passing `VREMLY_API_KEY` through.

## Keeping a local install current

The OpenAPI document ships inside the server, so a fresh `npx` install always
carries the specification as of the last release. `npx -y` re-resolves the
repository, so removing the cached copy picks up the newest server:

```bash
rm -rf ~/.npm/_npx && # then restart your assistant
```

Pin a tag instead if you would rather decide when that happens.
